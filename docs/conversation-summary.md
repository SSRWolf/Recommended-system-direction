# 对话摘要与候选研究路线

整理日期：2026-10-14
性质：对讨论内容的归纳，不是逐字聊天记录。

## 1. 背景与目标

- 人工智能专业硕士，掌握 Python / PyTorch，主要经历是课程项目和论文实验。
- 希望找到 AI 应用端实习，同时选择能延续组内积累、具备研究价值的论文方向。
- 讨论从推荐算法综述、博士论文阅读，逐步聚焦到推荐 Agent，以及它与组内时序推荐工作的结合。

## 2. 推荐 Agent 具体做什么

在本次讨论中，推荐 Agent 指以语言模型为交互与决策组件，结合用户信息、记忆以及检索和排序工具完成推荐的系统。例如：

1. 理解用户需求与约束。
2. 必要时追问，获得当前偏好。
3. 从历史行为中检索相关偏好记忆。
4. 调用商品查询、候选召回、过滤和排序工具。
5. 生成有依据的推荐及解释。
6. 记录反馈，更新后续推荐所需的信息。

参考项目包括 InteRecAgent、RecMind，链接见[阅读清单](reading-list.md)。

传统序列推荐、Decision Transformer 推荐和大模型工具调用各自承担不同角色。使用 Transformer 架构本身不意味着系统具有语言模型 Agent 的能力。

## 3. 论文研究与应用项目的区别

一个可运行的推荐助手可以展示工程能力；要形成研究论文，还需要：

- 明确的问题与可检验假设。
- 与有竞争力的方法进行公平对比。
- 合适的数据、评价指标、消融实验与误差分析。
- 说明性能改进来自何处，以及成本和适用边界。

无法仅凭“推荐 + Agent”的题目判断发表难度。加入多个智能体或调用大模型，也不能自动构成创新。原有综述和学位论文中的未来工作需要重新查新。

## 4. 组内资料与候选方向的关系

以下是对提供的本地文件内容的分析，不代表确认了各作者当前的研究安排。

| 材料 | 原始研究重点 | 可衔接方向 | 当前优先级 |
|---|---|---|---|
| 梁方宇《时序行为的状态建模与表征学习》 | 潜在行为状态、时段内及跨时段依赖、下一周期推荐 | 用户状态表示、时间上下文相关的记忆选择 | 高 |
| 王文萃《融合跨时段行为状态信息的用户时序偏好学习》 | NeuralTMT、跨时段行为转移、时间异质性偏好 | 状态感知的偏好检索、周期性兴趣与当前需求区分 | 高 |
| User Retention-oriented Recommendation with Decision Transformer（DT4Rec） | 离线轨迹、长期留存目标、推荐列表决策 | 长期推荐策略与奖励设计 | 中，取决于轨迹数据 |
| A Survey on the Fairness of Recommender Systems | 用户侧质量、物品或提供者侧曝光、公平性评价 | 公平约束、重排与群体评测 | 可作为单独切口 |
| 陈伟霖《融合结构知识的因果推断方法研究》 | 因果结构、网络干扰、长期效应估计 | 推荐策略长期因果效果评估 | 较依赖方法和数据支持 |
| 李梓健《因果驱动的领域自适应算法》 | 表示解耦、结构对齐、跨域迁移 | 跨场景偏好迁移与鲁棒推荐 | 间接相关 |

### 时序状态与偏好

梁方宇的工作涉及 HR-SSL、VI-SSL，重点是潜在状态和依赖关系，任务是下一周期各时间段的推荐，不应直接等同于单个下一物品预测。

王文萃的工作通过 NeuralTMT 建模跨时段转移，使用 NYC、TKY、Gowalla、Weeplace 四个签到数据集。它们提供行为时序，但不提供现成的多轮对话或明确的临时需求标注。

这两条线可为 Agent 选择历史偏好提供基础，但对话交互、工具调用和记忆管理属于新增工作。

### 长期决策

DT4Rec 的原始动作是推荐列表。要研究“追问—检索—推荐”的动作选择，需要额外定义动作空间、奖励，并获得包含相应行为的轨迹。原始离线推荐数据不能直接证明追问策略有效。

### 因果与公平

因果效果判断需要合理的识别假设与数据设计，不能从一般聊天记录直接推导。公平性需要明确对象与指标，结果更多样也不自动意味着更公平。

## 5. 优先候选题目

**面向动态用户偏好的状态感知记忆检索与推荐**

流程：

历史行为 → 用户状态表示 → 偏好记忆选择 → 商品检索与排序 → 推荐与解释 → 反馈更新。

示例：用户平时偏好便宜的工作餐，但当前任务是寻找适合纪念日的餐厅。系统需要区分长期偏好、周期性习惯与当前需求，而不是机械复用全部历史。

### 可检验的问题

在相同记忆预算、模型和上下文预算下，依据用户状态选择记忆，能否改善推荐质量及对当前需求的适应性？

### 对比与评价

- 对比只选最近历史、语义相似检索、固定偏好摘要，以及查新后确定的相关记忆方法。
- 推荐评价可考虑 Recall@K、NDCG@K；具体指标需匹配任务。
- 应用评价可考虑约束满足率、工具调用成功率、延迟及调用成本。
- 如果研究多轮交互，再设计对话任务和交互评价；不将离线排序提升直接解释为对话或长期收益提升。
- 做状态模块、时间信息、记忆选择策略等消融，并检查数据划分是否存在时间泄漏。

上述是实验设计建议，尚未执行，也未验证新颖性。

## 6. AI 应用实习的衔接

讨论中的优先建议是补充 RAG / Agent 与 Python 服务开发能力，并利用推荐场景形成一个完整项目：

- 有明确商品目录和用户需求的推荐任务。
- 可调用的检索、过滤与排序工具。
- 可追踪的用户状态和记忆更新。
- API 服务、日志、评测集和部署演示。

已有 PyTorch 能力可用于偏好模型或排序组件；服务化、工具编排、评测与部署需要额外练习。这是基于个人背景的学习建议，不是招聘市场统计或录用保证。

## 7. 起步顺序与待确认项

1. 按阅读清单先建立推荐系统、序列推荐和对话推荐框架。
2. 找到组内可复用的原始代码、数据预处理及基线结果。
3. 复现一个时序推荐基线。
4. 查新后，仅选择一个状态或记忆问题开展改进。
5. 最后接入可运行的 Agent 应用并进行独立评测。

当时检查到本地 fcmp 目录中的 train.py、dataset.py 及若干模型文件为空文件，不能据此认为已有可运行实现；此项仅反映当时的文件状态。

优先确认的条件：导师支持、可用代码与数据、算力及 API 预算、目标投稿要求和完成时间。避免一次叠加因果、强化学习、公平性与多智能体，导致研究问题和归因不清。
